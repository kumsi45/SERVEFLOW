# Printer P3.2 trusted pairing backend handoff

Migration 273 is deployed. This document describes its database contract for a future trusted pairing backend. The backend, Owner pairing UI, bridge credential store, and physical printer transport are not implemented here. Migration 273 is authoritative if this document drifts.

## Trust boundary and identities

- A trusted Edge Function or equivalent backend holds the Supabase service-role key and uses Auth Admin APIs. The restaurant PC and Owner browser never receive that key.
- The Owner approval endpoint authenticates the Owner JWT, derives `verified_owner_user_id` from that JWT, and authorizes only the selected active restaurant. The database rechecks active Owner membership; the backend must not accept a caller-supplied owner ID as proof.
- The bridge generates a 256-bit random proof. The backend supplies only its 32-byte digest to SQL. The short human code needs server-side rate limits and a keyed digest so the stored digest cannot be used for offline guessing if privileged database contents leak. Do not log either raw value.
- Each completed pairing binds exactly one dedicated, non-staff Supabase Auth user to one `print_agents` row. Runtime RPCs identify that agent through `auth.uid()`; no agent UUID sent by the bridge can substitute for authentication.

## Pairing RPC sequence

All six provisioning RPCs below execute only for `service_role`; they have fixed `public, pg_temp` search paths and no anonymous or ordinary authenticated grants.

1. **Challenge creation:** `begin_print_bridge_pairing(requested_code_digest bytea, requested_proof_digest bytea, requested_bridge_name text, requested_ttl_seconds integer default 300) returns uuid`. The backend validates and rate-limits the request, generates the short code, hashes the code and proof, and stores only the digests. SQL accepts 32-byte digests, a 1–120 character name, and a 60–600 second TTL. It creates a `pending` pairing and a `started` event. The backend delivers the pairing ID and human code through the intended setup flow; it does not reveal the raw proof to the Owner UI.
2. **Owner approval:** `approve_print_bridge_pairing(target_pairing_id uuid, supplied_code_digest bytea, target_restaurant_id uuid, verified_owner_user_id uuid) returns uuid`. The backend authenticates the Owner and binds its JWT user ID to the final argument. SQL locks the pairing, verifies pending state, server expiry, code digest, and active Owner membership in the requested restaurant. It writes the restaurant exactly once, moves to `approved`, and records an event. The backend rate-limits wrong code attempts without logging codes.
3. **Bridge redemption:** `begin_print_bridge_redemption(target_pairing_id uuid, supplied_proof_digest bytea) returns table(restaurant_id uuid, bridge_name text)`. The backend authenticates the possession proof, supplies its digest, and rate-limits attempts. SQL locks the approved, unexpired pairing, moves it to `redeeming`, and returns its authorized tenant and name to the trusted backend. A repeated proof cannot restart redemption after that transition.
4. **Dedicated identity:** The backend creates or recovers one dedicated Auth user with Auth Admin, strong generated credentials, and no restaurant staff membership. Auth creation is outside the SQL transaction. Persist a safe pairing-to-Auth correlation in trusted provisioning state or Auth metadata so an ambiguous retry can find the same identity; never create a second usable identity for one pairing. Compensate or audit an orphan if SQL completion fails after Auth creation.
5. **Completion:** `complete_print_bridge_redemption(target_pairing_id uuid, target_auth_user_id uuid) returns uuid`. SQL locks the `redeeming`, unexpired pairing, calls service-only `register_print_agent`, binds the Auth user and agent, moves to `completed`, and records pairing and lifecycle events. A retry with the same Auth user returns the same agent ID. Another Auth user is rejected. Completion does not issue credentials.
6. **Credential delivery:** The trusted backend delivers only that dedicated agent's authentication/session material once over TLS to the bridge setup channel. It never returns service-role credentials. Store bridge credentials later under the Windows service account using the chosen protected store. If the one-time response is lost after completion, do not mint a second identity or replay the proof; recover the same identity only through a separately reviewed secure recovery policy, or start a new pairing and revoke the old agent and Auth identity.

`fail_print_bridge_redemption(target_pairing_id uuid, reported_code text) returns void` marks a `redeeming` pairing failed with a bounded structured code and event. `expire_print_bridge_pairing(target_pairing_id uuid) returns void` marks an expired pending/approved/redeeming pairing. Both are service-only. `cancel_print_bridge_pairing(target_pairing_id uuid, target_restaurant_id uuid) returns void` is available to an authenticated active Owner of the pairing's restaurant for approved/redeeming states. Cancellation during external Auth provisioning requires backend compensation.

## Authorization, revocation, and audit

- `owner_set_print_agent_printer(target_restaurant_id uuid, target_agent_id uuid, target_printer_id uuid, requested_enabled boolean) returns void` requires an active Owner of the restaurant, an active agent and printer in that tenant, and records an allow/remove lifecycle event. Assignments are many-to-many. The bridge cannot grant its own affinity.
- `owner_revoke_print_agent(target_restaurant_id uuid, target_agent_id uuid) returns void` disables the agent and records a revocation event. Existing leases remain recorded until expiry; claim, renewal, connection lookup, heartbeat, observation, and acknowledgement deny the revoked agent. The backend must also disable/invalidate the dedicated Auth identity and retry or surface failures of that separate Auth Admin step. Rotation provisions a replacement, checks it, then revokes the old identity.
- Pairing transitions live in `print_bridge_pairing_events`; registration, affinity changes, and revocation live in `print_agent_lifecycle_events`. Keep logs free of raw codes, proofs, passwords, refresh tokens, service keys, and full connection options. Define retention for expired pairings and observations before adding any cleanup job.

## Runtime RPCs already deployed

`claim_print_jobs(uuid, integer, integer)` requires the authenticated active agent and current printer affinity. `renew_print_job_lease(uuid, uuid, integer)` requires the current unexpired owned job and attempt, current affinity, a 15–300 second extension, and a ten-minute maximum claim lifetime. `heartbeat_print_agent(uuid, text, text)` accepts bounded semantic version and `windows` platform, returns server time, and records contact only. `report_print_printer_observation(uuid, text, text, boolean)` accepts authorized printer status `reachable`, `unreachable`, or `unknown` and a bounded error code; it does not change printer configuration or prove paper output. `get_claimed_print_job_connection_v2(uuid)` exposes the typed Windows queue name or network fields only under an active owned lease and current affinity. `acknowledge_print_job(uuid, uuid, text, text, text, integer)` retains P2 transport-acceptance semantics with `paper_output_confirmed=false`.

## Decisions to resolve before P3.2 release

Specify the Owner and bridge HTTP endpoints and their authentication, code attempt budgets, digest key management, Auth identity naming and recovery, one-time credential delivery after ambiguous network responses, cancellation/expiry compensation, Auth disabling and token invalidation, credential rotation, backend secret storage, and audit/retention policy. Review those decisions and test partial failures and replay before deploying the pairing backend.

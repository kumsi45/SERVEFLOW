## 4. Applications and businesses: separate entities, disconnected lifecycle

Candidate `platform_private.applications` has UUID, business/contact name and email, constrained `business_type` (`restaurant`, `cafe`, `hotel`, `bar`, `lounge`, `other`), previous-application self link, pending/approved/rejected state and coherent decision actor/time/reason/request ID fields. It has **no applicant Auth ID and no restaurant FK**. Its table supports a pending record with no business, but no current public writer was found. Candidate `public.restaurants` has stable UUID, name, unique slug and creation time (migration 001); neither its schema nor current private application records require an approved application. Older signup paths could create a business without one.

Migration 278 locks an application row, permits one pending-to-decided transition, and accepts an exact replay by request ID, actor, decision and reason. A conflicting decision returns `PT409`. The invitation table enforces one intent per application, with no usable token, expiry, consumption or delivery. Thus approval is idempotent as a **decision**, not as provisioning. Rejection cannot directly leave a tenant provisioned by that RPC because it provisions nothing; it also cannot revoke an independently existing tenant. Application history remains as rows and audit events, but there is no durable application-to-business lineage. Counting applications as businesses would be incorrect.

**Future lifecycle proposal:** submitted application with authenticated or verified applicant link → admin decision and audit → explicit invitation/owner acceptance where appropriate → idempotent, unique application-to-business provisioning → readiness evidence → separately authorized operational entitlement. Keep decision, tenant creation, membership and entitlement timestamps/actors distinct. Define what happens on retries, reapplication, rejected applications, partial failure and two concurrent approvals. This is not implemented in B0.

## 9. Proposed minimum typed read contract (future B1, not implemented)

Use a new versioned private, `SECURITY DEFINER` read RPC or carefully extended `platform_admin_read`, always calling `require_admin('inspect')`, with explicit columns and no direct table grant. All responses include `asOf: timestamptz`, `source: 'authorized_platform_query'`, and a typed `availability` value where data is unknown. **Status codes:** 42501 authorization; 22023 invalid filter/cursor; P0002 unknown ID; PT409 conflict for future writes; failures never become zero. Enforce server max query length 100, escaped literal search semantics, stable `(created_at DESC,id DESC)` keyset pages, default 25/max 50, opaque/versioned cursor bound to filter/search, and deterministic `nextCursor`. Exact counts must be computed server-side from the same documented snapshot/filter or explicitly marked unavailable; page length is not a total. Concurrent inserts/updates may change later pages; use an `asOf`/snapshot strategy or document drift and never present paged list as a stable full export. UUID ID lookup should be explicit. Avoid exposing Auth email, secrets or audit summaries beyond the review need.

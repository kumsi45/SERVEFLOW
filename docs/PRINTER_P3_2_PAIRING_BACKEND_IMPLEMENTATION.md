# Printer P3.2 pairing backend candidate

This is a local implementation candidate. No Edge Function, frontend, or database change has been deployed. Migrations 271–273 remain immutable; Migration 274 is not required by this design. The Windows service, protected credential store, and physical transport are outside this phase.

## Setup and trust flow

1. The authenticated Owner calls `print-bridge-owner` with `{action:"initiate",restaurantId}`. The backend verifies active Owner membership and returns a signed, five-minute `setupToken` containing Owner ID, restaurant ID, random nonce, and key version. The token is a short-lived capability intended for an Owner-controlled local setup channel to the bridge. It contains no service key or agent credential.
2. The bridge generates and keeps a random 256-bit proof locally. It calls public `print-bridge-pair` with `{action:"start",bridgeName,proof,setupToken}`. The backend verifies the signed token and active Owner membership, consumes its nonce through the durable atomic rate limiter, and calls service-only `begin_print_bridge_pairing`. It returns the pairing ID and ten-digit human code. The database receives only HMAC-SHA-256 digests of the code and proof.
3. The Owner checks the code displayed by the bridge and calls `print-bridge-owner` with `{action:"approve",restaurantId,pairingId,code,setupToken}`. The backend checks the Owner JWT, active membership, token Owner/restaurant, and rate budget. Migration 273 locks and approves the matching pending pairing. The Owner endpoint never returns the proof or agent credentials.
4. The bridge calls `print-bridge-pair` with `{action:"redeem",pairingId,proof}`. Migration 273 consumes the approved proof once and returns the tenant to the trusted backend. The backend creates one dedicated, non-staff Auth user, signs it in, completes the agent binding, and returns only that user's access and refresh session to this bridge call over TLS. The response has `Cache-Control: no-store`. The original proof cannot initiate another redemption.

The setup token may authorize only one challenge start. It is not a pairing approval: code comparison, Owner authentication, active membership, and explicit approval are still required. The token and human code should be transferred only over an Owner-controlled setup channel; the future Owner UI and Windows bridge need to implement that channel.

## Backend configuration and operations

Set `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `PRINT_BRIDGE_DIGEST_KEYS`, `PRINT_BRIDGE_EMAIL_DOMAIN`, `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`, and exact `PRINT_BRIDGE_OWNER_ORIGIN` as Edge Function secrets. `PRINT_BRIDGE_DIGEST_KEYS` is JSON such as `{"current":"v1","keys":{"v1":"<base64url of 32 random bytes>"}}`; never use the example placeholder. Keep previous key versions for the maximum outstanding pairing life (five minutes) plus clock/rollout margin, then remove them. The secret is never bundled into frontend code. Rotate the Redis credential separately.

`print-bridge-pair` and `print-bridge-reconcile` require `verify_jwt=false` in `supabase/config.toml`; their handlers enforce proof/setup-token or maintenance-key authorization respectively. `print-bridge-owner` retains JWT verification. The public endpoints have no wildcard CORS policy. All three functions require TLS at their hosted endpoint. The external Redis limiter uses atomic `EVAL` counters, HMAC pseudonymized keys, and fails closed when unavailable. It is an operational dependency and must be provisioned before deployment.

`print-bridge-reconcile` additionally requires the `PRINT_BRIDGE_MAINTENANCE_KEY` secret, sent in the `x-print-bridge-maintenance-key` header by a trusted scheduler or operator. Schedule it after deployment and monitor errors. It scans dedicated Auth identities, retains all bound/completed identities, and deletes only eligible unbound orphans after terminal failure/cancellation/expiry or a five-minute expiry safety delay. It deliberately retains identities with missing pairing state for investigation. Auth Admin pagination currently caps the scan at 100,000 users; review the scale before production.

## Failure and credential policy

Auth creation and SQL binding are separate transactions. The dedicated Auth email and metadata correlate identity to pairing. A duplicate/ambiguous creation fails closed; the reconciliation job can identify the orphan. Failure after a known create deletes the unbound identity and marks the pairing failed. A SQL completion timeout triggers a state check before any cleanup. If binding completed but the HTTP response was lost, the old proof cannot retrieve the session again. Recovery requires Owner revocation of the old agent and a new pairing. An expired or cancelled pairing cannot create a usable agent. The bridge must protect the delivered refresh token under its Windows service account before considering setup complete.

Owner `revoke` disables the agent in the database first, then bans its Auth user and replaces its password. A failed Auth ban is reported as `AUTH_REVOCATION_PENDING` and can be retried. `rotate` performs that revocation and requires a new pairing; the replacement is a new identity and agent. P2 leases expire under their existing rules, and a revoked agent cannot claim, renew, or acknowledge. Existing Supabase access JWTs may remain cryptographically valid until expiry; Migration 273's active-agent checks are the server-authoritative runtime gate. The implementation has not been exercised against a real isolated Auth/Redis/Edge stack, so deployment review must include that integration gate.
